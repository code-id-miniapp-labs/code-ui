**Code UI** (`@code-ui`) is a component library for **WeChat MiniProgram (`weapp`)** that pairs finite state machine logic with a slot-based Tailwind CSS theming system.

Building maintainable UI in WeChat MiniProgram often runs into platform friction: `styleIsolation` makes styling third-party components awkward, `<slot>` lacks fallback content and scoped data, `<root-portal>` breaks CSS variable inheritance, and strict bundle size limits punish heavy runtime abstractions. Code UI is designed specifically around these constraints.

## Inspiration

Code UI combines ideas from two projects and adapts them for the MiniProgram runtime and compiler toolchain:

- **[Zag.js](https://zagjs.com/)** — Interactive components (`c-select`, `c-input-menu`, `c-popover`, `c-drawer`, `c-pin-input`, `c-tabs`, etc.) are driven by deterministic finite state machines (`createMachine` & `connect`). All state transitions, value synchronization, and UI attributes live inside the machine rather than ad-hoc `Component({})` methods.
- **[Nuxt UI](https://ui.nuxt.com/)** — Styling is built on semantic design tokens (`primary`, `secondary`, `neutral`, `danger`, `success`, `warning`, `info`), automatic light/dark mode variables, and slot-based Tailwind Variants (`tv`). Components can be themed globally in `cui.config.ts` or customized per instance via the `ui` and `class` props.

## Why Code UI?

### 1. Predictable State with Thin Runtime Components
In many MiniProgram libraries, interaction state, timers, and `this.setData()` calls are scattered across component methods and observers. In Code UI, runtime components are thin adapters:
- State logic is isolated in pure TypeScript machines and unit-tested independently of the WeChat runtime.
- `@code-ui/miniapp` bridges machine state to MiniProgram's `setData`, batching updates and only syncing fields that actually changed.
- Simple presentational components (`c-card`, `c-badge`, `c-avatar`, `c-chip`, `c-divider`, `c-skeleton`) skip the state machine layer entirely so they carry no extra runtime overhead.

### 2. Slot-Level Tailwind Customization
Overriding styles across MiniProgram custom component boundaries usually requires `externalClasses` boilerplate or `!important` WXSS hacks. Code UI models every component as a set of named anatomy slots (`root`, `base`, `label`, `leadingIcon`, `content`, etc.):
- **Global overrides**: Configure default variants, slot classes, or `(defaultClass) => string` transforms once in `cui.config.ts`.
- **Per-instance overrides**: Pass `ui="{{ { root: '...', label: '...' } }}"` or `class="..."` directly in WXML. Conflicting Tailwind utilities are automatically deduplicated and escaped for `weapp-tailwindcss`.

### 3. Build-Time Work Instead of Runtime Overhead
WeChat MiniPrograms have strict subpackage and main-package size budgets. `@code-ui/plugin-vite` shifts heavy work to compile time:
- **On-Demand Theme & CSS Injection**: Scans your project for used `<c-*>` tags and injects only the Tailwind classes and CSS variables needed by those components.
- **Auto-Imported Components**: Automatically registers used `<c-*>` tags in each page or component's `.json` `usingComponents` field.
- **Compile-Time Slot Detection**: WeChat's `<slot>` does not support fallback content (`<slot>default</slot>` is ignored by the platform). The compiler statically inspects your WXML templates and injects active slot flags so components know whether to render prop content or named `<slot>` content without manual boolean props.

### 4. Built for WeChat MiniProgram Quirks
- **`<root-portal>` Theme Inheritance**: Overlay components (`c-modal`, `c-drawer`, `c-popover`, `c-action-sheet`) rendered inside `<root-portal>` automatically inherit active CSS variables and dark mode state from `<c-app>`.
- **Compound Component Linking**: Multi-part components (`c-tabs`, `c-accordion`, `c-stepper`, `c-checkbox-group`, `c-radio-group`) support both declarative WXML composition and data-driven `items="{{...}}"` arrays using native MiniProgram `relations`.
